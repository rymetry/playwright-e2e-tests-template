# Test Design 入門ガイド

このディレクトリの仕組みを、初めて読む人向けに解説する。本書は規則を新設しない。
規則の正は [README.md](README.md)（管理ガイド）であり、本書と矛盾する場合は
READMEが優先する。用語は [README 1.2](README.md#12-用語集) を参照する。

## 1. 全体像

```
Suite（機能領域 = Area）
└── Parent Case（1つのユースケース = 1つのTest Design Doc）
    ├── 品質リスクとテスト条件（何を確認するか。どのCheckまたは下位レベルで担保するか）
    └── Check（1つのシナリオ × 1つのExecution mode。正常系／準正常系／異常系のいずれか）
        └── spec（PW／API Checkの実装。Playwrightテスト）
```

1つのCheckは次の道をたどる。矢印の下の数字はREADMEの参照節。

```
Doc生成 ─▶ 探索（任意）─▶ 本記入 ─▶ 期待値レビュー（人間）─▶ 実装 ─▶ EVALUATING ─▶ Qualification ─▶ ACTIVE
 6.0        6.0            6          6                       8       4              4.1              4
                                                                                                        │
      QUARANTINE ◀─ ヒール（失敗の分類 → Proposal → 人間の承認 → 適用 → 再Qualification）◀─ 失敗 ◀──┘
        4.3           6.1
```

JSTQB（ISTQB）のテストプロセスとの対応:

| JSTQBの活動 | このディレクトリでの成果物 |
|---|---|
| テスト分析（何をテストするか） | Parent Caseの「品質リスクとテスト条件」表 |
| テスト設計（どうテストするか） | Checkの「シナリオ」「Assertion設計」「前提・データ」 |
| テスト実装（実行可能にする） | spec（`e2e/<area>/*.spec.ts`）と「実行契約」 |

## 2. 1つのCheckの一生（E2E-DEMO-001-PW-01を例に）

1. **生成**: `test-design` workflow（起動方法は [AGENTS.md](../AGENTS.md)）が
   `npm run create:test-design -- --parent-id E2E-DEMO-001 --title "..." --slug docs-navigation --check PW:SMOKE:正常系:NONE:<探索不要の理由>`
   を実行し、Doc [E2E-DEMO-001-docs-navigation.md](e2e/demo/E2E-DEMO-001-docs-navigation.md)
   を作る。IDと章構成はこの時点で確定し、Statusは`DRAFT`から始まる。
2. **本記入**: 目的、品質リスク、テスト条件表、シナリオ（Given／When／Then）、
   Assertion設計、前提・データを埋める。テンプレートは短い。書いていない項目は
   README 9章の既定を採用したという意味になる（「省略は既定」）。既定と違うことを
   するときだけ、実行契約の「既定からの逸脱」に書く。
3. **期待値レビュー**: 人間が仕様と突き合わせ、「レビュー済みの期待値」表を埋める。
   AIが観測した挙動は、この表に入るまで期待値ではない。
4. **実装**: spec [E2E-DEMO-001.spec.ts](../e2e/demo/E2E-DEMO-001.spec.ts) を書く。
   テストタイトルはCheck IDで始め、本文のステップコメントはシナリオと対応させる。
   StatusをEVALUATINGにする。
5. **Qualification**: `npm run test:qualify -- --grep "E2E-DEMO-001-PW-01" --project=chromium`
   で3回clean passすると、結果を「Test Status判定根拠」表に記録してACTIVEにする。
   `npm run check`がDocとspecの整合（Status、Tier、分類、タグ）を検証する。
6. **失敗したら**: `heal` workflowが失敗を分類する。Locator・待機条件・テストデータ準備の
   劣化だけを修正提案し、期待値やシナリオには触れない。プロダクト不具合の疑いは
   報告してQUARANTINEを提案する。修正を適用したCheckは再Qualificationを経てACTIVEへ戻る。

## 3. テスト設計の考え方

### 分類の見分け方（README 1.3）

分岐の**原因**で判断する。期待動作が仕様に書かれているかどうかでは判断しない。

| 例（ログイン） | 分類 | 理由 |
|---|---|---|
| 正しい資格情報でログインできる | 正常系 | 基本フロー |
| パスワードを誤るとエラーが表示され、再入力できる | 準正常系 | 利用者の入力に起因する想定内の分岐 |
| 認証APIが5xxを返してもフォーム入力が失われず、再試行できる | 異常系 | 外部要因で処理を継続できない状況 |

仕様が沈黙している挙動（例: 5xx時の文言）は期待値を発明せず、「対象外・未確定」に残す。

### 技法の選び方

- リスクが高い条件ほど厳密なカバレッジ（境界値分析、デシジョンテーブルテスト）を使い、
  リスクが低い条件や仕様が曖昧な領域は経験ベース（エラー推測、探索的テスト）で補う
- E2Eに置くもの、unit／INTへ委ねるもの、異常系と模擬の扱いは
  [README 1.3](README.md#13-テスト条件分類技法) の「レベル分担」に従う

### 複数の代表値を1つのCheckで確認する

同じ分類・同じ経路なら、1つの`test()`の中で`test.step`ごとに値を分ける。分類が
異なる値は別Checkにする。Check IDに対応するテストは1件、が整合チェックの前提。

### 分類をレポートに出したい場合

タグは増やさない（README 7章「消費者のないタグを作らない」）。HTMLレポートで見たい
場合だけ、任意でannotationを付ける。

```ts
test('E2E-AUTH-001-PW-02: 誤ったパスワードでエラーが表示される',
  { annotation: { type: '分類', description: '準正常系' } },
  async ({ page }) => { /* ... */ });
```

## 4. レビューで見る箇所

Docのレビューは、ISTQB Advanced Test Analystのテストケース品質基準に沿って
次を確認する。

| 基準 | 見る節 |
|---|---|
| 正確性（仕様と一致する） | レビュー済みの期待値、Assertion設計 |
| 実行可能性（前提が揃えば実行できる） | 前提・データ、実行契約 |
| 必要性（リスクに対応している） | 品質リスクとテスト条件 |
| 理解可能性（第三者が読める） | シナリオ、カバレッジアイテムの理由 |
| トレーサビリティ（条件→Check→specが追える） | テスト条件表の担当、Check一覧、specのタイトル |
| 一貫性（同じ条件を二重に保証しない） | 実行契約の役割分担、対象外・未確定 |
| 精密さ（判定が観測可能） | Assertion設計、判定基準 |
| 完全性（未確定が明示されている） | 対象外・未確定 |

`npm run check`が機械的に読む節は「メタデータ」「Check一覧」「探索目的」「探索サマリ」
「Test Status判定根拠」で、表の行名を変えると検証に失敗する。

## 5. FAQ

**探索で見た挙動をそのまま期待値にしてはいけないのはなぜか。**
観測はバグを含む現状であり、意図された仕様とは限らないため。観測は「探索サマリ」に、
期待値は人間のレビューを経て「レビュー済みの期待値」に書く（README 5章、6章）。

**探索不要（`NONE`）の理由に書けない語は。**
`理由`、`TBD`、`TODO`、`未記入`、`未定`、`なし`は理由として扱われない（README 6.0）。

**`npm run check`が失敗した。よくある原因は。**

| メッセージ | 直し方 |
|---|---|
| 分類「…」は不正な値です | Check一覧の分類を正常系／準正常系／異常系のいずれかにする |
| Check一覧に「分類」列がありません | README 9.4に従い、Check IDの直後に列を追加する |
| Status=…ですが、対応するテストがspecにありません | specを追加するか、StatusをDRAFTに戻す |
| 「…」のStatusが不一致です（Check一覧: … / 判定根拠: …） | Check一覧と「Test Status判定根拠」の判定を同時に更新する |

**古い形式のDocはどう移行するか。**
必須はCheck一覧への「分類」列の追加だけ。節の統合はDoc改訂時に任意で行う（README 9.4）。
specと期待値を変えなければ再Qualificationは不要。

**どのworkflowをいつ使うか。**
Docの新規作成は`test-design`、実装前の観測は`explore`、失敗の分類と修復は`heal`。
起動方法は [AGENTS.md](../AGENTS.md) を参照する。

**間欠的に失敗するテストはどう扱うか。**
ヒールは待機条件の不備に因果証拠がある場合だけ修正する。証拠がない揺れは
「flaky疑い」としてQUARANTINEを提案し、タイムアウト延長やretryで隠さない（README 6.1）。
